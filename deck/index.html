    The brief

    OpenTable wants more search sessions to end in a booking

    Its discovery notes describe two diners. The prototype was built around both.

    The diner who knows the restaurant

    ruths chris denver

    Names are hard to spell, and chains have several locations in one city. Success is the right location on the first try.

    The diner who is exploring

    (empty box) + Mexican + $30 and under

    No name in mind yet. Success is a short, trustworthy list to browse and narrow.

    Metric that mattersSearch to booking. Better results are the means, not the end.
    Summary

    What changes, in five lines

    Diners who know the restaurant find it on the first try

    Misspelled, run-together and partial names work. A chain's locations are labeled; the best rated comes first.

    Diners who are exploring can browse before they type

    The page opens on top rated restaurants nearby. Cuisine, price, dining style and city narrow the list.

    Results start local

    Ranked by distance from the diner's approximate location, no permission prompt. Distance reorders, never hides.

    Most of the gain came from reshaping the data

    Algolia handled typos with its defaults. The data held search back; a repeatable script fixes it before indexing.

    Next: connect search to bookings

    The prototype shows better results, not yet more bookings. Next phase: click and conversion tracking, then A/B tests.

              How it was built

              A repeatable preparation script, then a front end small enough to explain line by line

              source

              Two files

              restaurants_list.json (15 fields) and restaurants_info.csv (8 fields), same 5,000 restaurants.

              01-merge

              Join

              On objectID. Stops if any ID is missing from either file. Numbers typed as numbers.

              05-transform

              Reshape

              Split names, group cuisines, one price, quality score. 19 fields per record.

              02-index

              Upload

              5 batches of 1,000. Whole record replaced, so reruns are safe.

              site/

              Search page

              InstantSearch.js from a CDN. Three files, no build step, GitHub Pages.

              Why this scope. The provided starter used Parcel 1 and Node 9. A plain page with nothing to compile was less to break on deploy day.

              Left for later, not half built: sorting, natural language search, click analytics.

              Index configuration

              A name match beats a cuisine match, which beats a place. Quality breaks ties.

              Searchable attributes, in order
              1. 1name, brand
              2. 2cuisines, food_type_raw
              3. 3city, neighborhood, area
              4. 4dining_style
              5. 5unordered(name)
              6. 6unordered(cuisines)
              7. 7unordered(city)

              Order set from using the live OpenTable site to reach specific restaurants and chain locations. Search data would inform a better one.

              Ranking criteria (Algolia default order)
              typo›geo›words›filters›proximity›attribute›exact›custom

              Custom: desc(quality_score), then desc(reviews_count)

              Facets
              cuisines, city (searchable), price_label, dining_style, neighborhood
              Typos
              Default: 1 from 4 letters, 2 from 8
              Stop words
              English, removed from the query
              Optional
              and, the, of, in, at
              Synonym
              brazil = brasil
              No results
              removeWordsIfNoResults: allOptional

              Set by hand in the Algolia dashboard. Read-only export in config/index-settings.json.

                A break I caused, found by the tests

                "mccormick and schmicks" dropped from 10 results to 0. In the untuned index, "and" had been matching the price text "$30 and under". Naming the searchable attributes removed that accidental match.

                Appendix B · The data

                Eight source fields left out, and why

                FieldWhy it was left out
                countryAll 5,000 records say "US". One value carries no information.
                phone, phone_numberThe two files disagree on 160 records, and the card shows no phone.
                mobile_reserve_urlSame restaurant ID as reserve_url, which the card uses. 2015 scrape, untested.
                priceDisagrees with price_range on 220 records. The text is what the diner sees.
                postal_code1,614 distinct values, not searched, filtered or shown.
                stateNot searched, filtered or shown. City, area and coordinates carry location.
                payment_optionsNot searched, filtered or shown.
                Price conflict, real record

                Vinotopia Restaurant and Bar

                price: 2   price_range: "$50 and over"

                The diner sees "$50 and over", so the text wins and price_band is derived from it.

                On zip codes

                Adding postal_code back is one line and a reindex. Searching it well is harder: a typo in the first digits points to a different part of the country, so typos would need to be allowed only in the last digits.

                Appendix F · Assumptions and run it yourself

                What I assumed about the data, and how to rebuild it

                Same objectID, same restaurant

                Every ID is in both files. The merge stops if one is not.

                A spaced dash splits brand and location

                True for 1,086 names. One known exception left: "Star of Honolulu - Five Star".

                Price text beats the number

                220 conflicts. The text is what the diner sees.

                Few reviews say less

                Ratings pulled toward the 4.29 average until reviews add up.

                Neighborhood left as delivered

                Equals city in 2,491 records. The card shows the city once.

                Links untested

                Images and reservation links from 2015. Grey placeholder when an image fails.
